## 2. 背景与目标

围绕 IP 优选建立一个管理系统，将配置来源、执行优选、分阶段筛选、查看结果、更新 DNS、发送通知和追溯执行记录串成闭环。

目标是让使用者通过同一管理入口完成手动与定时优选，以及后续结果处理。成功标准复用已确认规则，不新增耗时、吞吐或提速比例承诺：

- 能保存不同来源与规则的独立任务，按手动或已启用计划进入既定队列，完成候选获取、预算约束、测速、筛选和排序；受控输入下可按第 8 节检查数量、边界与判定。
- 能查看全部合格结果及候选来源、当次快照、判定原因与真实进度；DNS／通知遵守明确目标和开关，失败不篡改优选结果，不静默换方式、覆盖其他记录或扩大权限。
- 认证、归档、历史保留、删除恢复及 Docker 持久化符合共享范围与生命周期；异常、外部未确认结果及系统内关键操作可按各自记录追溯，不将共用身份当作真实个人身份。

## 3. 用户、认证与业务规则

### 3.1 使用者

- 面向个人自用，或由可信小团队共同使用。
- 所有使用者共用一个管理密码，不要求独立账号。
- 所有任务、配置和记录共享，不划分个人数据空间。
- 不需要独立角色、菜单权限、操作权限或按使用者区分的数据权限。
- 共用身份不等于公开访问：管理功能和数据仍受密码认证保护。

### 3.2 认证方式

- 系统使用密码认证。
- 管理密码支持随机生成，或通过配置（环境变量）设置。
- 密码环境变量优先；有配置则使用该密码，修改后重启生效。未配置时每次启动重新生成随机管理密码，供部署管理者在本机受保护的初始化流程获取；重启即更换，旧随机密码不继续生效。
- 未配置环境变量时不能从持久化数据恢复旧随机密码来绕过每次启动重生成。忘记密码通过配置环境变量并重启重置，不提供独立账号找回流程；不在普通运行、历史或通知日志中暴露明文密码。
- 登录会话最长有效期为 7 天，到期重新认证；退出登录结束当前会话。修改密码或重启后重新生成随机密码时，全部旧会话失效，不能仅依赖旧会话到期。
- 同一来源 15 分钟内累计 5 次登录失败后冷却 15 分钟，不锁定其他来源的全站访问；提示失败和剩余冷却，不记录输入的明文密码。反向代理下来源识别等实现由技术方案处理。
- 具体受保护的初始化密码获取入口由技术方案落实；本轮不实际生成或索取管理密码。
- 共用密码不能可靠区分真实操作人；已确认增加第 3.13 节的轻量统一操作日志，主体仅标识共享管理身份或系统，不伪造个人归属，不宣称可证明真实操作人。既有运行事件与简要删除日志继续保留。

### 3.3 明确不做

- 独立账号注册、邀请和账号管理。
- 按个人设置角色或权限。
- 不同使用者之间的任务、配置和记录隔离。

### 3.4 任务配置与记录边界

- 支持创建和保存多个独立优选任务，而不是只提供一套全局优选配置。
- 每个任务分别保存 IP 来源、过滤规则、定时计划和推送目标。
- 过滤后的 IP 可以由使用者手动选择并推送至 DNS 服务商；任务也可以分别开启 DNS 自动推送，初始默认关闭。
- 首期 DNS 服务商限定为阿里云云解析 DNS，由系统直接对接服务商的 DNS 管理能力。
- 首期支持 A 和 AAAA 两种 DNS 记录：IPv4 候选写入 A 记录，IPv6 候选写入 AAAA 记录。DNS 推送只替换 IP，保留目标记录原有 TTL、解析线路和其他设置，不提供覆盖这些属性的任务选项。
- 多个任务可绑定同一 DNS 记录，所有指向该目标的实际写入须串行，后一次明确推送按顺序生效；记录最近写入任务／执行和时间，人工从旧历史推送前提示可能覆盖更新值，不以历史较旧为由静默改选其他目标。
- 用户先选择阿里云账号下已有的域名，再从现有 A／AAAA 记录中选择 DNS 更新目标；只更新明确选择的现有记录，不因记录不存在而自动创建新记录。
- DNS 写入失败时保留现有目标记录中的地址，不清空 DNS；明确提示并留存失败记录，不自动重试，允许用户手动重试。
- DNS 请求超时或连接断开而无法确认服务端结果时，标记为“结果未确认”，不声称旧 IP 仍未变化；系统尝试读取并核对明确选中的记录。核对确认已写入则记录成功，确认未写入则记录失败；仍无法核实时不自动重写、不回滚、不改选其他记录，由用户决定是否手动重试，并提示可能重复写入。
- DNS 推送只修改使用者明确选中的目标记录，以本次选中的优选 IP 替换该记录的旧 IP，并保留其他 DNS 记录不变。
- 任务启用自动推送后，手动或定时运行成功都会触发自动推送。每条启用的 DNS 记录只选择任务排序后的第一名地址：IPv4 写入对应的 A 记录，IPv6 写入对应的 AAAA 记录。若某条记录找不到匹配地址族的优选 IP，不修改该记录；若整次运行没有任何合格 IP，保留现有 DNS 记录，并将自动推送标记为未推送。
- 每个任务可以独立选择启用哪些过滤步骤、设置条件并调整顺序；首期默认依次启用延迟、丢包率、下载速度三项过滤。
- 新任务默认使用 ICMP Ping，使用者可按任务改选 TCPING；ICMP 不可用时须明确提示，不自动改用 TCPING。
- 每次执行使用入队时固定的过滤配置；首期过滤项目、参数及排序选项已按第 3.7 节确认，后续编辑不影响旧执行，不额外引入地区等首期未包含的过滤项目。
- 每个任务可配置结果排序方式；默认延迟从低到高，延迟相同时下载速度从高到低。
- 任务选用的 ICMP Ping 不可用时，系统必须明确提示并让使用者手动改选 TCPING，不自动改变测速方式。
- “全部 IP 段”表示使用项目已有的内置网段清单，而非扫描互联网上所有 IP 地址。当前项目默认 IPv4 清单为 `ip.txt`，另提供 `ipv6.txt` 作为 IPv6 来源；该 IPv6 清单仅收录部分网段，不代表 Cloudflare 全部 IPv6 网段。
- 选择内置清单表示将该清单的全部网段纳入来源范围；网段内的地址按抽样配置选取，不表示逐个遍历全部 IP。新任务默认开启 IPv4、关闭 IPv6；只有使用者明确开启 IPv6 后，IPv6 来源才能纳入候选、测速及追加采样。
- 指定 IPv4／IPv6、网段、第三方域名和优选 IP 可以加入任务配置；域名按本次实际开始时解析，成功来源继续、失败来源不回退旧候选，非敏感定义与本轮来源事实按第 3.8～3.9 节留存。
- 多个选定的 IP 来源合并成同一组候选 IP；完全相同的 IP 地址只测速一次，同时保留该 IP 命中的全部来源标记，便于查看候选来源和追溯结果。
- 配置的第三方优选域名作为候选来源：在优选执行中查询其 DNS 地址记录，将解析出的 IPv4／IPv6 地址加入任务候选池，再按既定规则去重和保留来源标记。
- 不同任务的配置互不覆盖，可以分别维护不同优选方案。
- 每次运行生成一条归属该任务的历史记录；一个任务可以对应多条执行记录。
- 多任务的配置与记录独立；首期全局只允许一个优选任务运行，其他任务触发后排队等待，避免同时测速互相干扰。
- 执行入队时保存非敏感配置快照；任务后续编辑不修改旧执行。移除任务采用归档，不级联删除历史；有排队或运行执行时禁止归档，须先等待结束或单独取消。
- 归档任务保留可查配置和历史，不接受新手动或定时触发；可恢复，恢复时定时默认关闭。归档和恢复不撤销外部 DNS 或消息，历史仍按保留期管理。

### 3.5 候选 IP 抽样与邻近扩采（本轮范围已确认）

#### 3.5.1 默认值与配置范围

| 配置项 | 默认值 | 约束 |
| --- | --- | --- |
| IPv4 | 开启 | 只纳入已启用地址族的来源与候选 |
| IPv6 | 关闭 | 须使用者主动开启，不因选择域名或配置 AAAA 目标而自动开启 |
| 每个 CIDR 的初始抽样数 | 256 | 可按网段覆盖，整数范围 1～100000；小网段不足时受实际地址数限制 |
| IPv4 累计候选上限 | 10000 | 每任务独立配置，整数范围 1～100000 |
| IPv6 累计候选上限 | 10000 | 与 IPv4 分别计数，整数范围 1～100000 |
| 扩采预留比例 | 扣除定向 IP 后剩余预算的 20% | 整数分配见第 3.5.2 节；初采未用完的名额可转为扩采 |
| 扩采触发排名 | 各地址族初始有效延迟结果前 10% | 人数向上取整，延迟相同按 IP 数值顺序决定，不额外扩大名额 |
| 邻近扩采范围 | IPv4 /24、IPv6 /120 | 单个邻近范围最多 256 个地址，网段来源的边界约束见第 3.5.4 节 |
| 扩采轮次 | 最多一轮 | 尽量补测命中范围的未测地址，新结果不递归触发下一轮 |

数量是候选 IP 数，不是同一 IP 的探测次数；0 不表示无限制，非法数量应拒绝保存并说明原因。这些默认值属于产品初值，不是已实测的耗时、内存、带宽容量或可达率保证。

#### 3.5.2 地址族预算及初采分配

以下计算对每个已启用地址族分别执行，两个地址族不共享或互借名额。默认只启用 IPv4，最多纳入 10000 个候选；两族都开启且沿用默认值时，合计最多 20000 个。

1. 将已启用来源解析为标准化的 IP 和 CIDR；定向候选包括手动指定 IP、手动填写的优选 IP、域名解析 IP。相同 IP 合并为一个候选，并保留全部来源标记。
2. 设本地址族累计上限为 `B`，去重后定向候选数为 `D`。先为定向候选保留名额；任一已启用地址族 `D > B` 时，本次任务明确报错，不截断定向来源、不启动测速或 DNS 推送；使用者调整来源或上限后重试。
3. 定向候选占满预算但未超限（`D = B`）时，可完成这些定向候选的测试，不再增加网段初采或扩采。
4. 计算剩余预算 `R = B - D`。`R = 0` 时网段初采名额 `I = 0`；`R > 0` 时 `I = min(R, max(1, floor(0.8 × R)))`，预留名额为 `R - I`。这使通常约 20% 留给扩采；只剩 1 个名额时优先初采。
5. 初采名额 `I` 在去重后的已选 CIDR 之间尽量平均分配，受每段请求抽样数及可取地址数限制。小段用不完的名额可分给仍有需求的其他网段；整数余数按固定网段数值顺序（网络地址、前缀长度）分配，不以来源文件行顺序作为优先级。
6. 先分配数量再生成候选，不先展开超大网段的全部地址再截断。与定向候选、其他网段重复的 IP 不重复占名额；只在允许范围内尽量补足各段配额，不能补足时保留实际数量，不越界或重复凑数。
7. 设实际新增的去重网段初采数为 `S`，满足 `S ≤ I`。初始候选共 `D + S` 个；扩采可用名额 `E = B - D - S`，因此包含预留名额和未用完的初采名额。
8. 扩采新增的去重候选数记为 `X`，始终满足 `X ≤ E` 和 `D + S + X ≤ B`。候选测试失败或被过滤淘汰后也不返还已用累计名额；总量不是“当前仍合格的 IP 数”。

#### 3.5.3 初始延迟排名与扩采触发

- 在初始候选按任务所选方式实际完成延迟测量后，IPv4、IPv6 分别对成功测得有效延迟的结果排名；未得到延迟值、测试失败的 IP 不参与排名。
- 本地址族有效初始结果数为 `N`；`N = 0` 时不扩采，否则取 `K = ceil(0.1 × N)` 个触发 IP。按延迟升序、相同延迟时按标准化 IP 数值升序取前 K 个，不把并列 IP 全部加入。
- 扩采排名仅用于决定在哪里追加，采用原始有效延迟数值而非界面四舍五入值；它不替代最终的合格结果排序，也不承诺触发者达到某个绝对低延迟毫秒阈值。
- 基础延迟探测始终执行，不因关闭延迟或丢包门槛而停止；没有成功延迟结果、没有剩余预算或命中范围均已测完时不强行扩采，记录原因，不暗中更换测速方式。

#### 3.5.4 邻近范围、优先级与单轮结束

- 每个触发 IP 对应其所在 IPv4 /24 或 IPv6 /120 邻近范围。由网段抽样触发时，还须限制在相应原来源 CIDR 内；原网段小于邻近范围时不能向网段外扩张。
- 仅来自手动指定或域名解析的触发 IP，即使未命中任何已选 CIDR，也允许在完整邻近范围内扩采。配置界面及执行记录必须明确这会新增用户未逐个填写的 IP，并展示触发 IP、范围与来源；不冒充手动指定来源。
- 多个触发 IP 命中同一邻近范围时合并为一个扩采单元；将允许的地址范围合并去重，仍保留各来源对范围的约束。相同 IP 不重复测速或领取预算。
- 扩采单元按其最佳初始触发 IP 的延迟升序处理，延迟相同时按邻近网段数值升序决定。先尽量补齐最好单元的未测地址，再处理后一个；若当前单元也不能补齐，只追加剩余预算允许的数量，预算用尽后停止。
- 初始抽样超限时采用“网段均衡缩减”，扩采预算不足时采用“最好延迟子网优先”，两者不能混为同一策略；后续较慢子网可能完全不扩采，应在记录中说明。
- 扩采候选属于本轮新增候选，不能反过来作为新的“定向 IP”占用优先配额；扩采只运行一轮，新结果不再触发递归扩采。
- 初采与扩采采用相同的延迟、丢包筛选口径；下载固定在初始和扩采合并筛选之后，每地址族最多选择本任务配置数量的候选测速。未选中下载且下载过滤启用的候选不视为最终合格。完成下载过滤与最终排序后才自动推送 DNS，不得在扩采未结束时提前推送初始第一名。
- 没有新地址、预算不足或条件未命中时，允许少于上限结束；不为用满上限而重复测试、跨范围追加或启动下一轮。

#### 3.5.5 数量展示与验收示例

- 运行详情按地址族展示上限、去重定向数、初采请求数与实际分配数、初采新增数、有效延迟数、触发数、扩采范围及优先顺序、扩采新增数和未用额度。对去重、初采缩减、定向超限、扩采未发生或未补齐的原因提供可追溯说明。
- 预算示例：`B = 10000`、`D = 100` 时，`R = 9900`、`I = 7920`、初始预留 1980。若实际新增初采 `S = 7000`，则可扩采 `E = 2900`，不是仍限制在 1980；本地址族最终累计不超过 10000。
- 取整示例：`R = 9` 时初采 7、预留 2；`R = 1` 时初采 1、预留 0；`R = 0` 时都不再新增。
- 排名示例：某地址族有 11 个有效初始延迟结果，取前 2 个触发 IP；只有 1 个有效结果时取 1 个；没有有效结果时不扩采。若触发者来自同一邻近范围，该范围只处理一次。
- 范围示例：若某 IPv4 /24 的 256 个地址已在初采全部测试，后续即使排名命中也不新增或重复测速；原来源为更小的 /28 时，网段触发的追加范围仅限该 /28。仅手动 IP 或域名触发时，按已确认规则可以扩展到对应 /24 或 /120。
- 超限示例：上限 10000 而本地址族定向 IP 去重后有 10001 个时，任务报错，不自动只保留前 10000 个。

### 3.6 定时计划与并发运行规则（本轮范围已确认）

- 定时计划按任务保存，支持快捷周期和高级 Cron 两种设置入口。
- 新建任务的定时开关默认关闭；保存时间配置不等于开启定时，须由使用者主动开启。关闭定时时仍可手动运行任务。
- 关闭定时开关只停止该任务后续定时触发，不取消已入队执行，也不打断正在运行的执行；取消或停止须使用独立操作。定时开关不替代 DNS 自动推送开关，保留的执行或新手动执行仍遵循其 DNS 推送配置。
- 快捷周期覆盖每天、每周、每隔若干分钟或小时；高级 Cron 用于表达更复杂的运行时间。
- Cron 使用“分、时、日、月、周”五字段格式，最短触发周期为 1 分钟，不支持秒字段或秒级触发；快捷周期采用相同的最短周期限制。
- 所有计划使用统一系统时区，默认 Asia/Shanghai（北京时间），允许通过系统配置修改；界面须明确显示当前计划时区，不能因为容器默认 UTC 而静默改变执行时间。
- 首期全局只运行一个优选任务；不同任务同时触发时，其余任务进入等待队列，不并行测速。
- 运行席位覆盖取得席位后的完整执行及自动收尾，不在测速结束或结果保存后提前释放：本轮来源获取、测速、筛选及结果保存结束后，仍须完成按配置执行的 DNS 自动推送、必要的既定结果核对及结束通知，再允许等待队列中的下一执行开始。
- 自动收尾结束指各目标／渠道已得到本轮成功、明确失败、结果未确认或跳过等处理结论；未启用或不符合推送条件的步骤记为跳过，不为等待推送成功或人工重试而继续占位。DNS 核对仍不能确认时沿用未确认保护规则，不自动重写；后续人工重试不恢复原执行或重新占用其席位，同目标 DNS 写入仍须串行。
- 同一任务已经运行或排队时不新增执行实例，也不额外排队：重复的定时触发跳过并记录原因；手动触发则明确提示“任务已在运行或排队”。
- 原执行的自动收尾尚未结束时，同一任务仍按忙碌处理，不因已有优选结果而允许再次触发；连接变更、任务归档和运行记录删除也继续遵守活动执行保护，直至该执行收尾结束。
- 不同任务按触发后进入等待队列的先后顺序执行；手动与定时触发不区分优先级，不抢占正在运行的任务。
- 固定间隔计划按固定时间表触发，不从上一轮完成时间重新计时；上一轮耗时不改变后续计划时点，同任务到点仍处于运行或排队状态时按重复触发规则跳过。
- 系统离线或 Docker 停机期间错过的定时计划，恢复后不补跑；按原计划显示并等待下一次执行时间，使用者仍可手动触发。
- 容器重启后不恢复旧执行：原运行中的执行标记为“已中断”，原排队中的执行标记为“已取消”，保留重启导致中断或取消的原因；不会自动重跑或重新入队。恢复后仅接受新触发或等待下一计划。
- 使用者可以取消排队中的执行，也可以停止正在运行的执行；确认取消后不再发起新的 DNS 更新或其他业务推送。唯一自动消息例外是：向该执行已启用的每个通知渠道各发送一次“已取消”结束摘要，未启用的渠道不发送。停止前已成功写入的 DNS 或已发送的消息不自动撤销。
- 不按运行时长自动终止优选，也不设置自动超时停止规则；任务将持续运行至完成、失败或被使用者手动停止。长任务可能持续阻塞等待队列，应在界面中保持运行状态可见，并提供已确认的手动停止能力。
- 停止请求与停止完成不能混为一谈：已取得席位的执行须确认测速等执行活动真正停止，妥善记录已发起外部操作的已知或未确认结果，并完成允许发送的取消摘要处理后才释放席位；不能仅收到停止请求就启动下一执行，也不等待人工重试。取消尚在排队中的执行不为发送取消摘要而占用或抢占其他执行的运行席位。
- 重复的定时触发只记录跳过事件和原因，不创建新的运行实例；取消、中断和手动触发被拒绝的原因需要可追溯。
- 开启定时、保存已启用任务的新计划或修改系统时区后，以本次变更成功生效的时刻为界，按有效计划和当前系统时区重新计算严格晚于该时刻的下一次运行时间；不立即试跑，不补跑已过去的时点。
- 新计划生效后只由新时间表产生后续触发，旧计划尚未发生的未来时点不再生效；此前已排队或运行中的执行不被取消、不改变队列顺序，也不因计划变更新增重复执行。
- 修改统一系统时区时，按同一规则重算全部已启用任务的未来时点；关闭定时的任务只保存配置，不因保存计划或改变时区而自动启用或运行。
- 输入不符合五字段 Cron 或最短周期限制时，应拒绝保存并明确说明原因，原有有效计划和启停状态保持不变，不静默转换执行频率。

### 3.7 测速指标与过滤判定（逐项确认）

- 第一版支持延迟、丢包率、下载速度三类可选过滤项目；可分别启用并配置。延迟与丢包过滤的相对顺序可调，下载若启用则固定在初始及扩采候选完成前置测量和筛选之后，不再允许任意前移。
- 延迟采用同批成功探测耗时的中位数，统一用于延迟过滤、结果排序和扩采排名；成功次数为偶数时取中间两值的平均，只有一次成功时取该次耗时，使用未四舍五入的实际数值判断。
- 丢包率按同批失败次数／实际总探测次数计算；失败不作为 0 毫秒或其他延迟数值参与中位数。全部失败时该 IP 不可用，不进入有效延迟结果、最终合格结果或扩采触发排名。ICMP 统计回复失败，TCPING 统计连接探测失败，不声称直接测得链路丢包。
- 每个 IP 默认进行 5 次延迟探测，每次最多等待 1000 毫秒；次数和单次等待时长允许按任务修改。单次超时计为一次失败，不因此切换协议；该设置不是整项任务超时，不改变“不自动超时终止任务”的已确认规则。
- 新任务默认依次开启延迟→丢包率→下载速度：成功探测中位延迟不高于 200 毫秒、失败比例不高于 20%、下载速度不低于 5 MB/s；等于门槛时通过。开关和阈值可修改，调序仅限上述阶段约束内。
- 速度统一使用十进制 MB/s，1 MB 为 1000000 字节；不能把 Mbps 或 MiB/s 的原始数值当成同一个单位比较。默认阈值是产品初值，不代表已经验证的最优筛选或吞吐保证。
- 默认延迟方式为 ICMP Ping，可按任务切换 TCPING；环境不支持 ICMP 时明确提示。TCPING 默认目标端口为 443，合法端口为 1～65535 的整数。
- 每次运行按已启用地址族分别限制下载测速候选，IPv4、IPv6 默认各最多 20 个，可按任务修改；初采和扩采共享本次下载候选额度，不分别领取额外 20 个。
- 初始与扩采候选合并，并完成已启用的延迟和丢包过滤后，按中位延迟升序、同延迟按标准化 IP 数值升序统一预选下载候选；不依赖尚未测得的下载速度，也不让初始阶段提前用尽下载名额。未实际下载的候选标记未测试，不显示为速度 0，也不视为已通过启用的下载过滤。
- 下载测速每次只测一个候选 IP，默认单个 IP 的有效下载测量窗口最多 10 秒，时长可按任务修改；速度为实际成功读取字节数／有效下载时间的平均值，不采用单秒峰值。
- 下载平均速度的有效计时与配置测量窗口均从开始读取文件正文时启动，正常结束于文件完整下载或达到窗口上限；建立连接、TLS 握手及等待响应头的时间不纳入下载速度分母，也不消耗正文测量窗口。正文计时启动后的等待或停滞仍计入实际经过时长，不只累计有数据到达的片段；达到配置窗口主动结束采样不等同网络异常断流，实际连接或读取错误仍按失败处理。
- 每个候选 IP 的正文前等待采用独立时长上限，默认 10 秒，允许按任务配置为 1～60 的整数秒；从发起该 IP 的下载连接起累计计算建连、TLS 握手及等待响应头的合计时间，不是每个阶段各有 10 秒。超时仅将该 IP 标记为下载失败并记录原因，结束该 IP 的本次尝试，继续处理其他候选；不自动终止整项优选，也不消耗开始读取正文后独立计算的测量窗口。非法时长拒绝保存，不静默修正原配置。
- 正文读取期间不设置额外的连续无数据超时，仅受该 IP 已配置的正文测量窗口限制。窗口到期时，只要实际成功读取正文的字节数大于 0、实际有效测量时长大于 0，且未发生真实连接或读取错误，即可按包含全部停滞时间的实际经过时长形成平均速度样本，再按原速度门槛筛选；这属于测量窗口结束，不标为文件已完整下载。全程零字节或无法形成有效正时长时，标记下载失败并说明原因，不伪造 0 速度、无穷大速度或有效样本；继续其他候选。
- 测速文件在配置的最大测量窗口届满前正常完整下载时，允许作为有效下载样本，按实际成功读取字节数／实际有效测量时长计算平均速度，再按原下载速度门槛判定；不把配置窗口当作实际时长，也不为凑满窗口重复下载。允许参与筛选不等于自动通过速度门槛。
- 提前完整下载的样本保留实际读取字节数、实际有效测量时长及提前完成标记；窗口结束与提前完整下载分别留存结束原因。网络错误、异常断流仍按下载失败处理，即使已经读取部分数据，也不以该部分数据冒充正常有效样本或提前完整下载。
- 下载连接或读取失败须明确标记失败和原因，不能伪造为 0 速度；未获得有效下载结果的候选不通过启用的下载过滤。下载窗口不是任务整体超时，不改变已确认的不自动终止长任务规则。
- 下载地址默认沿用项目当前 DefaultDownloadURL（Parallels 下载文件），允许每任务覆盖为自己的 HTTP／HTTPS 测速文件 URL。其当前可用性尚未实测；配置或测速失败须明确报告，不静默更换 URL 或测速方式。
- 下载测试以候选 IP 为实际连接目标，URL 提供对应的文件请求目标；不能退化为对管理服务器普通下载带宽的测试。具体连接、重定向和 TLS 实现留给技术方案，不将默认第三方地址视为可用性承诺。
- 最终结果可选两种排序：延迟优先（中位延迟升序、同延迟下载平均速度降序）和速度优先（平均速度降序、同速度中位延迟升序）；默认延迟优先，以上键均相同时按标准化 IP 数值升序稳定排列。
- 基础 ICMP／TCP 延迟探测始终执行并产生延迟中位数与失败比例；延迟、丢包过滤开关只控制是否按对应门槛淘汰，不停止基础测量。即使两项门槛均关闭，全部探测失败的 IP 仍不可用。
- 整个下载步骤可关闭；关闭时不下载，速度字段留空并标记未测量，最终只可采用延迟优先排序，此时相同延迟按 IP 数值排序，不把缺失速度当作 0。保存“下载关闭＋速度优先”组合时须提示并阻止保存，不能静默改变用户选择。
- 探测次数为 1～100 的整数，单次等待为 100～10000 毫秒，下载窗口为 1～60 秒；默认仍分别为 5 次、1000 毫秒、10 秒。下载候选数量为正整数，启用时不得大于相应地址族预算；超出须提示并拒绝保存，不静默改数。
- 失败比例门槛为 0～100%，延迟上限为大于 0 的有限数（毫秒），速度下限为大于等于 0 的有限数（MB/s）；无穷大、非数字及越界值明确拒绝。关闭步骤保留其配置值，但不据此执行停用步骤。
- 地区筛选不纳入首期，保留结果范围见第 3.8 节。

### 3.8 结果与运行记录（逐项确认）

- 主结果列表保留全部通过已启用筛选的 IP，不自动只保留前 10 名；结果可分页展示，DNS 每条目标记录仍只写一个匹配地址族的 IP。
- 支持在指定任务内查询该任务的运行记录，不混入其他任务；可按入队时间范围、运行主状态、手动／定时触发方式，以及独立的 DNS 阶段状态和通知阶段状态筛选。时间范围以实际入队时间判断，不以实际开始或结束时间代替，尚未开始就取消的记录也可命中。
- 已设置的多个筛选条件须同时满足，未设置的条件不限制对应维度。DNS 状态筛选按该执行任一目标记录命中所选状态匹配，通知状态筛选按任一渠道命中所选状态匹配；同时设置 DNS 与通知条件时，两类条件分别有命中才返回该执行。优选主状态与投递状态分开判断，可以筛出优选已完成但 DNS 失败或通知结果未确认的记录，不把未启用或未推送误当成功或失败。
- 运行记录列表直接展示以下摘要：记录 ID、手动／定时触发方式、入队时间、实际开始时间、自动收尾结束时间及执行耗时；主状态、当前阶段及席位是否仍忙碌；各地址族的合格 IP 数量与最佳合格 IP；DNS 以及 Telegram、企业微信各自的投递状态摘要。这些是最低摘要信息，不要求全部铺成表格列，完整指标和明细仍进入详情查看。
- 正常执行的耗时从实际取得席位开始，包含本轮自动收尾；运行中显示当前已用时，收尾结束后显示该段实际耗时。未开始、尚未结束或中断后无法确认的时间、耗时和结果须如实标记未产生、未知或不适用，不用 0、当前时间或伪造的结束时间补齐；确已统计为 0 的合格数量可正常显示为 0。
- 各地址族最佳 IP 取该族本轮最终合格结果按已确认排序规则排列的第一名，不取未完成筛选的临时首个候选；未启用地址族、尚未形成最终结果及已确定无合格 IP 应分别说明。即使优选主结果已确定，DNS／通知仍在自动处理中时，列表仍显示当前阶段及席位忙碌，不能只显示已完成而误导为可再次触发。
- DNS 状态摘要须保留部分失败或结果未确认等异常信息，不因其他目标成功而全部显示成功；Telegram 与企业微信分别显示渠道结果，不以单一成功概括全部渠道。列表摘要不包含秘密凭据，详细目标与逐渠道投递记录仍可进入详情查看。
- 运行中自动更新排队位置、等待时长、当前阶段及运行已用时。队列位置按当前等待队列计算，下一位取得席位的执行为第 1 位，不将正在占用席位的执行算作排队成员；等待时长从本次入队起算，运行已用时从实际取得席位起算，持续包含自动收尾。
- 按已启用地址族和实际阶段展示已处理数量／本阶段已知总量，并标明计数单位；来源获取以来源项、候选测量或筛选以 IP、DNS 以目标记录、通知以渠道呈现实际进展。单个 IP 的探测批次或下载尝试得到本轮结论后才计为该阶段已处理，成功、失败或跳过应按实际结果说明；已处理不等于合格，合格数量另行展示。
- 总量尚未确定时显示已知处理量及总量待确定，不把候选上限、下载配额或预计扩采量当成实际总量；阶段切换或扩采新增候选时说明对应阶段及数量变化。首期不提供总体百分比或预计剩余时间，不用固定比例或虚构进度掩盖未知总量。
- DNS 按目标、通知按渠道自动更新本轮处理进展及阶段结果；测速已经结束但收尾尚未完成时仍展示 DNS／通知当前阶段及席位忙碌。进度展示不改变主状态、外部结果未确认保护或取消规则，也不因测速数量已全部处理就提前释放席位。
- 运行详情保留本次实际纳入预算的全部候选汇总：来源、测量指标、通过／淘汰／未下载／测试失败状态和原因；不要求保存每次探测的原始报文。
- 每个候选 IP 的详情按本次入队时固定的配置快照展示过滤步骤的顺序、启停状态及阈值，并对照本轮实际汇总指标，给出各步骤判定与原因。停用的步骤明确标记停用，不当作通过；因前序淘汰而未执行的后续步骤、未进入下载配额的未测候选等须说明未执行或未测试的原因，不把缺失指标当作 0 或据此伪造门槛判定。
- 仅本轮最终合格 IP 展示该地址族的最终名次，依据当次快照中的排序模式及已确认并列规则排列；未合格或未测试候选不伪造合格结果名次。后续修改任务规则不改写历史判定、阈值或名次；已有来源、抽样扩采统计、非敏感快照及 DNS／通知明细仍保留并可查看，不新增原始探测报文保存要求。
- 保留候选不代表额外增加下载量或重复测试。运行入队时固定非敏感任务配置快照，任务后续编辑只影响新执行；历史仍可查看当时的来源定义、测速与过滤规则、排序及非敏感推送设置，不明文复制密码或 Token。
- 域名候选仍在本次实际开始时解析；将实际取得的候选和来源状态与本次快照关联，不能以任务当前配置替代历史事实。
- 只允许删除已结束的执行记录，排队或运行中的记录须先取消或停止。删除需二次确认，先移入回收站并隐藏正常列表，7 天内可恢复；到期清理该记录的候选、快照和推送详情，保留简要删除操作记录。
- 删除或恢复记录不修改任务配置，不回滚已写入 DNS，也不撤回已发送消息；删除是本系统历史数据生命周期操作，不是外部操作撤销。
- 历史默认按执行结束时间保留 30 天，可修改；未结束的执行不自动清理。超过保留期进入 7 天回收站，到期再清理详情。回收站恢复后重新起算保留期，原执行时间不改写，不因数据恢复重发 DNS 或通知。

### 3.9 来源刷新与失败（本轮主要规则已确认）

- 域名候选按每次运行开始时的 DNS 解析结果获取，不直接把上次保存的候选当作本次新结果；正常 DNS 缓存和解析器的技术细节不在此阶段指定。
- 部分已选来源失败，但本轮其他来源仍取得候选时，只使用成功来源继续；失败来源不回退上次 IP，清楚展示失败来源和原因。
- 本轮全部来源均无法提供任何候选时，任务明确失败，不进行测速或 DNS 推送；这与流程完成但没有合格 IP 的结果不同。
- 仍遵守定向候选超预算时本次任务失败的规则，不能以部分来源继续为由截断定向 IP 或绕过预算。

### 3.10 服务连接与敏感配置（主要方式已确认）

- 阿里云 DNS、Telegram 及企业微信连接作为可命名的全局共享配置维护，任务保存引用，不要求每个任务重复填写相同凭据。
- 页面只显示凭据已设置或脱敏状态，敏感值可替换但不能明文回读；历史快照和普通运行日志不得复制密码、Token 或带密钥的 Webhook。
- 被任务配置引用的连接不得直接删除，须先解除任务引用；排队或运行实例引用该连接时，不允许修改会影响执行的凭据或目标，须等执行结束或取消。历史快照只记录非敏感标识，不恢复连接的执行权限。
- 空闲且无活动执行引用时可替换凭据；账号、机器人或群等目标身份变更按新连接处理并重新绑定，不能静默替换旧引用或扩大原选中的 DNS 记录范围。

### 3.11 消息通知（逐项确认）

- 每个任务可同时启用 Telegram 和企业微信，每种渠道选择一个已配置的全局服务连接；新任务两种通知均默认关闭，配置连接不自动发送测试消息。
- 消息通知开关与 DNS 自动推送相互独立，关闭消息不关闭 DNS；每个渠道分别留存发送状态，不因为另一个渠道失败而抹掉已送达事实。
- 仅在执行结束汇总一次：成功、无合格结果、失败、取消或中断均可向已启用渠道发送；不为排队、开始或重复触发跳过事件发送消息。同一结束事件不因页面刷新或重启重复发送。
- 取消摘要是停止后不再发送新业务消息的明确例外：排队取消或运行停止确认后，已启用渠道各最多发一次“已取消”摘要，不恢复测速或 DNS 更新；摘要发送失败仍按既定规则留痕，不自动重试。
- 摘要包含任务标识、结束状态、合格数量、各启用地址族的最佳 IP 汇总指标及已知 DNS 结果，不含密钥或完整调试日志；没有速度或合格地址时如实标记，不伪造指标。
- 用户可手动发送指定可用运行记录的摘要。通知明确失败或超时结果未确认时均留存原因，不自动重试，可单独重发该渠道，不重跑优选或 DNS。未确认不等同未送达，手动重发须提示可能产生重复消息。
- 失败提示与投递记录须脱敏，不能把第三方错误中的 Token、Webhook 密钥或认证请求原文原样展示。真实 Webhook 和 Token 不写入需求示例。

### 3.12 Docker 数据持久化与恢复（主要规则已确认）

- Docker 容器与持久化数据分离；任务、全局服务连接、受保护凭据、运行历史、回收站及轻量操作／简要删除日志保存在独立挂载数据卷，容器重建或正常升级不应清空。
- 数据可通过卷级备份恢复；恢复须包含安全保存凭据所需的保护材料，但不要求首期提供网页备份向导。存储介质、迁移、密钥及备份实现由技术方案明确。
- 恢复数据不恢复旧执行的运行权，不补跑或重发旧 DNS／消息；按已确认规则将原运行与排队实例标记中断或取消。未配置环境变量时，每次启动依然生成新随机密码，不从备份恢复旧随机密码或其登录权限。

### 3.13 轻量统一操作日志（已确认）

- 首期增加轻量统一操作日志，保留既有运行／跳过／取消／中断事件与简要删除日志，不以新增日志替代原运行记录、快照或投递明细，也不增加独立账号及权限层级。
- 记录系统内的关键动作：任务／来源／过滤及排序配置的创建或变更、任务归档及恢复、定时计划保存与启停、共享连接创建／凭据替换／删除、手动或系统触发与停止、DNS／通知推送及重试、优选记录删除／恢复／到期清理，以及系统内时区和保留设置变更。不记录普通列表查询、详情浏览等只读操作，不承诺捕获系统外部配置编辑或识别真实个人。
- 字段为事件发生时间、共享管理身份或系统这一主体类别、动作、对象的非敏感标识、动作本身的结果及脱敏原因；可关联任务、执行、连接或投递明细便于追溯，不复制完整测量数据或敏感请求。触发已受理不等于优选成功，投递结果未确认不伪造为失败、成功或未写入。
- 所有已认证使用者均可查看，支持按事件时间范围、动作、对象及结果筛选，已设置条件同时满足，未设置条件不限制该维度。未认证不可查询；不提供逐条修改或删除操作日志、简要删除日志的能力。
- 操作日志及简要删除日志从各自事件发生时刻起独立固定保留 30 天，首期不提供改期选项；过期自动清理，不进入运行记录回收站。原运行事件和历史仍按既定的可配置保留期及 7 天回收站处理，不因日志到期而删除或恢复关联任务、历史、DNS 或消息；被清理运行记录的简要日志仍按自身事件时间保留。
- 凭据替换只记动作发生，不保存旧值、新值或秘密材料；密码、Token、含密钥的 Webhook、会话凭证、完整认证请求或含秘密的错误原文均不得进入日志。对象使用非敏感标识，不以带密钥地址冒充对象名称；错误原因在保存和展示前脱敏。
- 日志随数据卷持久化及备份恢复，恢复不改写原事件时间或重新起算其 30 天保留期，不重放日志对应的触发、DNS 或通知；已过期条目继续按既定规则清理。只读查询与日志清理不改变优选主状态或其他已确认业务事实。

## 5. 管理对象与建模输入（业务语义）

本节归并已确认的对象、来源、关系和生命周期，不指定物理表、外键、接口或页面。主状态定稿时点和轻量操作留痕均已确认；本节业务语义已随 v1.0 整体确认冻结。

| 对象 | 定义与来源 | 已确认关系及生命周期 |
| --- | --- | --- |
| 优选任务 | 使用者维护的来源、地址族、测速、过滤、排序、计划及推送配置 | 一个任务对应多次执行；编辑只影响新入队执行，活动执行期间禁止归档；归档不删配置或历史、不接受新触发，恢复后定时关闭 |
| IP 来源配置 | 内置清单、CIDR、手动／优选 IP 及域名等任务配置；解析与扩采事实由本轮执行产生 | 多来源合并去重，同一 IP 保留全部来源标记；定义进入非敏感快照，实际解析和触发范围属于本轮事实，失败不回退旧候选 |
| 执行记录与快照 | 手动或定时入队产生的一次独立执行，系统记录触发方式、时间、主状态、阶段及当次规则 | 每条记录归属一个任务，不以新运行覆盖旧记录；关联候选和投递明细，活动执行不可直接删除，结束后按 30 天保留及 7 天回收站规则处理 |
| 候选及优选结果 | 本次实际纳入预算的 IP、来源、测量汇总、判定、原因及合格排名，由优选过程生成 | 同一执行内同一 IP 合并；初采扩采共用分族预算，全部候选可查；最终合格 IP 才有该族名次，历史测量及判定不可当作可编辑配置 |
| 全局服务连接 | 可命名的阿里云、Telegram、企业微信连接，由使用者维护目标身份及受保护凭据 | 多个任务可引用同一连接；Telegram、企业微信每任务每种各选一个；先解绑才能删除，活动引用期间保护凭据和目标；秘密不进入快照且不可明文回读 |
| DNS 更新目标 | 用户从已连接账号明确选择的现有 A／AAAA 记录，目标不是由优选自动创建 | 多任务可共享目标，实际写入串行；只换匹配地址族 IP，保留 TTL、线路等属性及其他记录；历史引用不授予任意新目标权限 |
| DNS／通知投递明细 | 关联执行、目标记录或通知渠道的实际处理结果，由系统产生 | 各目标／渠道独立保留成功、失败、未推送或未确认；人工重试不重跑优选、不覆盖其他成功事实，删除历史不撤销外部操作 |
| 系统设置与认证会话 | 统一时区、历史保留设置、共用密码来源及登录会话等系统配置和状态 | 所有认证使用者共享管理范围；密码重启与会话失效按第 3.2 节执行，不形成独立账号或个人权限 |
| 轻量统一操作日志 | 系统内关键写入、执行和投递动作的时间、共享管理身份／系统、动作、非敏感对象、结果及脱敏原因，由系统产生 | 与运行历史独立，认证后只读可查且可筛选，不可逐条改删；操作／简要删除日志按事件发生时间固定保留 30 天，过期不进回收站，卷恢复不重置事件时间或重放动作 |

### 5.1 核心字段、字典与可编辑性

- 任务保存地址族开关、来源及数量预算、测速方式和参数、过滤步骤／启停／门槛、排序、计划及定时开关、DNS 目标和消息连接引用；默认值、类型、合法范围和组合按第 3.5～3.7 节执行，不另设隐藏默认值。
- 任务、执行与共享连接须稳定区分；执行保存任务归属、触发方式、入队及实际执行时间、快照、主状态及阶段结果，不能因改名或编辑误指其他对象。具体标识及字段命名由技术方案确定。
- 触发方式为手动／定时，地址族为 IPv4／IPv6，排序为延迟优先／速度优先；七种主状态见第 6.3 节，计划启停、归档及回收站生命周期不新增第八种主状态。
- 测量、时间、计数、判定、名次及投递结果由系统按事实生成，用户通过既定操作触发变化，不直接改写历史数值或当次规则。未知、未测、失败、未启用和真实为 0 的统计须分开说明。
- 快照只保存非敏感配置和引用标识；当前任务不能替代旧执行事实，历史引用不恢复连接的执行权限。密码、Token、Webhook 密钥不回读、不进入普通日志、快照或通知。

### 5.2 关系与联动

- 任务与执行、执行与候选是一对多，一个候选可关联多个来源标记；执行按目标／渠道关联投递事实，任务通过引用使用全局服务连接。
- 任务归档不级联删除历史；记录回收站期间保留关联候选、快照及投递详情供恢复，到期清详情后保留既定简要删除日志，不撤销 DNS 或消息。
- 所有管理行为遵守共用密码的同一认证范围，不划分个人数据或权限；秘密保护对全部使用者一致。轻量操作日志按第 3.13 节独立留存，不能借日志恢复已删除对象或推断真实个人；本节已获用户整体确认，可作为后续建模与设计的业务输入。

## 6. 主流程与状态边界

已确认主流程：保存任务配置 → 手动或定时触发、入队固定非敏感快照并按队列执行 → 获取已启用地址族的本轮来源（含实际解析）→ 去重保留定向 IP、校验上限并分配初采预算 → 初始测试及按延迟排名触发最多一轮邻近补测 → 按当次快照完成过滤与最终排序 → 保存优选阶段结果 → 按条件更新 DNS 并发送启用的结束摘要 → 正常自动收尾结束后按优选结论定稿主状态并释放席位；停止、重启按既定取消和中断规则处理。

- DNS 推送可人工选择结果后执行，也可按任务开启自动执行；自动开关初始关闭，开启后对成功的手动和定时运行均生效。每条自动推送记录只取对应地址族排序第一名；无合格 IP 时保留原记录并标记未推送。DNS 写入失败须明确报告并留存失败记录，不自动重试，可手动重试。
- 取消、重启恢复及不自动超时见第 3.6 节。优选结果状态与 DNS／通知投递状态分别记录；流程正常结束但没有合格 IP 标记为“无合格结果”，与执行故障“失败”区分。运行进度按第 3.8 节展示分阶段真实计数、队列位置及耗时，不提供总体百分比或预计剩余时间。
- 优选已成功而 DNS 更新或通知发送失败时，保留优选成功及其结果，独立展示相应推送失败；允许仅重试失败推送，不要求重新测速。各目标或渠道的实际成功与失败分别留存，不混成“优选失败”。
- 已结束记录经二次确认后进入 7 天回收站，可恢复；排队或运行记录不能直接删除。该操作不影响已写入 DNS 或已发通知，明细保留及清理见第 3.8 节。

### 6.1 调度相关状态与联动（已确认部分）

本表补充排队、取消、中断及重复触发行为；完整运行主状态见第 6.3 节，DNS／通知阶段结果仍独立记录。

| 当前状态 | 触发事件 | 后续状态或处理 | 联动与记录 |
| --- | --- | --- | --- |
| 排队中 | 前一执行的全部自动收尾结束并释放席位，轮到本次执行 | 运行中 | 全局仍最多一个运行实例，按入队顺序开始 |
| 排队中 | 使用者取消 | 已取消 | 从等待队列移除，保留取消原因，不测速或更新 DNS；仅允许已启用渠道各一条取消摘要，不占用其他执行的席位 |
| 运行中 | 使用者要求停止，且执行确认已停止 | 已取消 | 不再发起 DNS 或其他业务推送，仅允许已启用渠道各一条取消结束摘要；已成功外部操作不撤销，确认停止且取消收尾结束后才释放运行席位 |
| 运行中 | 容器重启 | 已中断 | 保留中断原因，不自动重跑，也不恢复旧执行 |
| 排队中 | 容器重启 | 已取消 | 保留取消原因，不恢复原队列实例 |
| 运行中或排队中 | 同任务再次被定时触发 | 原状态不变 | 跳过本次触发并留痕，不生成新运行实例 |
| 运行中或排队中 | 使用者再次手动运行同任务 | 原状态不变 | 提示任务已在运行或排队，不生成新运行实例 |
| 运行中 | 运行时间较长 | 原状态不变 | 不自动超时终止，仍可由使用者手动停止 |
| 运行中 | 优选阶段已有结果，DNS／通知仍正常收尾 | 运行中 | 当前阶段指示收尾，已产生结果可查看，席位仍忙碌 |
| 运行中 | 全部正常自动收尾结束 | 已完成、无合格结果或失败 | 按优选阶段结论定稿，不以投递成功与否改写优选结果；释放席位后依 FIFO 启动下一执行 |

### 6.2 定时开关与计划变更状态

定时计划的启停状态与单次执行的排队、运行或取消状态分开管理，关闭计划不等于取消执行。

| 定时状态 | 操作与条件 | 操作后定时状态 | 未来触发与已有执行 |
| --- | --- | --- | --- |
| 关闭 | 开启已保存的有效计划 | 开启 | 从生效时刻之后寻找下一时点，不立即试跑、不补跑；已有执行不变 |
| 开启 | 使用者关闭定时 | 关闭 | 停止后续定时触发；已排队和运行中的执行继续，仍可手动触发 |
| 开启 | 有效新计划保存成功，或系统时区变更生效 | 开启 | 用新计划和当前时区重算未来时点，旧未来时点失效；保留已有执行及队列顺序 |
| 关闭 | 保存计划或修改系统时区 | 关闭 | 仅保存配置，不自动启用，也不自动运行 |
| 开启或关闭 | 尝试保存格式或周期不合法的计划 | 原状态不变 | 拒绝保存并明确提示，原有效配置不被替换 |

### 6.3 单次运行主状态与阶段状态（已确认）

- 一次运行只有一个主状态，用于记录列表展示和筛选；来源获取、测速、扩采、DNS 更新及通知的阶段结果独立记录，在详情中解释各阶段的实际结果。
- 主状态采用下表七种值；DNS 或通知失败、结果未确认，不覆盖已经成功的优选结果，也不把优选改为失败。
- 主状态与运行席位不能混为一谈：优选主结果已确定不表示自动收尾已结束。DNS 或通知仍在处理时，须展示当前阶段及尚未释放席位的忙碌原因；同任务重复触发和活动执行保护按第 3.6 节判断，不新增第八种主状态。
- 正常执行在 DNS／通知等自动收尾期间，主状态保持运行中，当前阶段显示正在进行的收尾，已经产生的优选结果仍可查看。各步骤得到本轮成功、失败、未确认或跳过等结论并完成既定收尾后，再按优选阶段结论定为已完成、无合格结果或失败，不要求全部投递成功。
- 自动 DNS 的条件是优选阶段正常完成且已形成匹配地址族的最终合格结果，不等待主状态先变为已完成；结束摘要可以使用已确定的优选阶段结论，不能因为当前主状态仍运行中就把它当作结束结论。摘要处理完成后再定稿，避免把收尾触发与主状态定稿互相作为前提。
- 收尾期间手动停止并确认停止时，主状态为已取消；期间因重启等被打断时，主状态为已中断。保留已产生的测量数据、合格结果和已知外部事实，不撤销成功操作，不把未确认外部结果伪造为未写入，也不自动重跑或重发；取消摘要和席位释放仍按第 3.6、3.11 节执行。原排队取消规则不变。

| 主状态 | 业务含义 |
| --- | --- |
| 排队中 | 执行已入队，尚未实际开始 |
| 运行中 | 本次执行正在处理，包含优选及正常自动收尾；详情显示当前阶段和已有结果 |
| 已完成 | 优选正常结束且有合格 IP，正常自动收尾已有结论；DNS 与通知是否成功分别查看 |
| 无合格结果 | 优选正常结束但无通过筛选的 IP，正常自动收尾已有结论；不等同系统故障 |
| 失败 | 来源全部无候选、预算校验或运行故障导致无法正常优选，记录原因；既定正常收尾完成后定稿 |
| 已取消 | 用户取消排队或停止运行且已确认停止；沿用重启时取消旧排队执行的规则 |
| 已中断 | 原运行实例因重启等被打断且不自动恢复，保留中断原因 |

- 阶段状态不替代主状态；来源部分失败可留警告并继续，DNS 和通知按目标／渠道保存成功、失败、未推送或结果未确认等实际状态。
- 单独重试失败推送只更新相关投递记录，不重跑优选、不抹去其他目标的成功事实，也不因重试而改写原优选结果。

## 8. 已确认部分的验收口径

- AC-02：不同使用者使用同一有效管理密码认证后，能访问相同范围的任务、配置和记录，不出现按个人划分的数据视图。

- AC-08：新任务默认只启用 IPv4；主动启用 IPv6 并选择其清单时，只纳入项目 `ipv6.txt` 实际列出的网段，不能将其描述为完整 IPv6 清单；全部内置网段纳入范围不代表逐 IP 全量测速。
- AC-09：同一任务的多个已配置来源经合并后，同一个完整 IP 地址只出现在一次实际测速候选中；该候选仍能查看它命中的全部来源标记。
- AC-10：第三方域名按本次实际开始时解析，将已启用地址族的结果纳入候选；重复地址只测一次并保留域名来源标记，失败及快照规则按 AC-61、AC-63 执行。
- AC-11：任务分别设置过滤开关和条件；默认延迟→丢包率→下载速度。延迟与丢包可调整相对顺序，下载启用时必须后置；不能前移到初始及扩采合并筛选之前。
- AC-12：每次优选结果可使用该任务配置的排序方式；默认按延迟从低到高排列，延迟相同时按下载速度从高到低排列。
- AC-13：任务支持选择 ICMP Ping 或 TCPING 作为延迟测试方式；选择 ICMP Ping 且运行环境不支持该方式时，系统明确提示 ICMP Ping 不可用，并让使用者手动改选 TCPING，不自动切换。
- AC-14：使用者可手动从过滤后的结果中选择 IP 并触发 DNS 推送；每条目标记录每次只能选择 1 个符合地址族的 IP。每个优选任务均可单独开启或关闭自动推送；新建任务的自动推送开关默认为关闭。任务开启自动推送后，手动和定时运行成功均会触发自动推送。

- AC-17：首期支持阿里云云解析 DNS 的 A 和 AAAA 记录；A 记录接收 IPv4，AAAA 记录接收 IPv6。
- AC-18：开启自动推送后，每次成功的手动或定时运行均会为每条启用的 A／AAAA 记录选择相应地址族排序第一名的 IP，并替换该记录中的旧 IP。该地址族没有合格候选时不修改对应 DNS 记录。
- AC-19：阿里云明确拒绝或明确返回未写入失败时，不清空或改选现有目标，不自动重试；显示脱敏原因并留存记录，可手动重试。超时或断连结果按 AC-78 核对，不能声称旧 IP 一定未变。
- AC-20：一次优选运行没有任何合格 IP 时，手动或自动推送均不修改任何现有 DNS 记录；自动推送标记为“未推送”。
- AC-21：使用者只能从已连接的阿里云账号当前已有域名和 A／AAAA 记录中选择更新目标。推送不自动创建 DNS 记录，不修改未勾选的记录。
- AC-22：任务按网段保存初采数量，按 IPv4、IPv6 分别保存累计候选上限；默认数值、计数口径和超限分配按第 3.5 节执行，不承诺逐 IP 全量测速，也不承诺运行一定用满上限。
- AC-23：每个任务可保存快捷周期或高级 Cron 定时配置；快捷周期包括每天、每周及分钟或小时固定间隔，Cron 使用分、时、日、月、周五字段，均不得小于 1 分钟。
- AC-24：计划统一使用系统时区，默认 Asia/Shanghai，允许通过系统配置修改；界面显示计划时区及下一次执行时间，不静默使用容器 UTC 替代。

- AC-26：不同任务按入队先后执行，手动与定时无优先级差异；前一执行按 AC-81～AC-82 完成自动收尾或取消收尾并释放席位后，才启动下一执行。
- AC-27：固定间隔按计划时间表推进，不从上一轮结束时重新起算；运行耗时不推迟后续时点，忙时跳过本次触发。
- AC-28：停机期间错过的计划不补跑，恢复后显示下一次计划时间；仍可接受新的手动触发。
- AC-29：重启后旧运行实例标记已中断，旧排队实例标记已取消，均保留原因且不自动恢复或重跑。
- AC-30：用户可取消排队执行和停止运行中的执行；确认取消后不再发起 DNS 更新或其他业务推送，仅允许已启用通知渠道各发送一次取消摘要作为例外，已成功的外部操作不自动撤销。
- AC-31：系统不因优选运行时间长而自动终止该执行；持续占用运行席位的执行可由用户手动停止，不暗中设置自动超时终止规则。

- AC-33：关闭定时时，不再产生该任务的新定时触发；原排队及运行中的执行保持原状，不因关闭定时而自动取消。手动触发和 DNS 自动推送配置不受该开关修改影响。

- AC-35：启用定时、保存已启用任务的新计划或变更系统时区后，下一运行时点必须严格晚于本次变更成功生效的时刻，使用有效计划和当前系统时区；不立即触发试跑或补跑过去时点，旧计划未来时点不再触发。
- AC-36：计划或时区变更不取消、不重复创建已排队或运行中的执行，也不改变其排队顺序；定时关闭的任务保存配置后仍保持关闭，不因配置变更自动执行。
- AC-37：未单独填写网段初始抽样数量时采用 256；网段实际地址数不足时不越界取样、不重复凑数。此默认值不代表自动启用未选择的 IPv4 或 IPv6 来源。
- AC-38：默认仅启用 IPv4，IPv4 与 IPv6 的累计候选上限配置值各为 10000；开启两族后预算独立，不相互借用名额。关闭的地址族不得产生初采或扩采候选。

- AC-40：同一地址族内，定向 IP、域名结果、网段初采及扩采重复的标准化 IP 只占一个累计名额，保留全部来源；测试失败和过滤淘汰不返还名额。
- AC-41：任何已启用地址族的定向 IP 去重后超过本地址族上限时，本次任务明确失败，不自动丢弃定向 IP，也不启动本次测速或 DNS 推送；等于上限时仅测试定向候选。
- AC-42：扣除定向名额后按第 3.5.2 节的 80% 向下取整分给初采，剩余留扩采；只剩 1 个时优先初采。初采实际未用完的名额可转扩采，任意阶段累计候选不超过相应地址族上限。
- AC-43：初采预算不足时按网段均衡缩减，受请求数量及可取地址数限制；小段剩余额度再分配，余数按固定网段数值顺序分配，不因文件行序改变优先级。
- AC-44：IPv4、IPv6 分别对初始有效延迟排名，取人数向上取整的前 10%，相同延迟按 IP 数值决定；11 个有效结果取前 2 个，0 个有效结果不扩采，不因并列扩大名额。
- AC-45：邻近扩采使用 IPv4 /24、IPv6 /120；网段抽样触发时不越出原来源 CIDR。仅手动或域名来源可触发完整邻近范围扩采，但须明确展示范围扩大和触发来源。
- AC-46：重复命中的邻近范围合并，按最佳触发延迟及固定网段数值顺序补测未测 IP；扩采预算不足时优先最好子网，耗尽即停，不重复测速、不重新领取预算。
- AC-47：最多追加一轮，新增结果不递归触发；初采及扩采遵循同一前置筛选配置，合并后统一选下载候选，未做启用的下载测试者不视为合格；最终过滤和排序结束后才自动推送 DNS。
- AC-48：运行详情按地址族展示预算、去重定向数、请求及实际初采数、有效延迟数、触发数、扩采范围和新增数、剩余名额，以及超限缩减、未扩采或未补齐原因；不承诺一定用满预算。
- AC-49：第一版提供延迟、丢包率和下载速度三类可选过滤，不要求地区筛选。各项条件可配置；延迟与丢包可调序，下载只能后置。默认三项均启用，门槛依 AC-52。
- AC-50：延迟取同批成功探测耗时的中位数，偶数成功次数取中间两值平均；失败次数计入失败比例，不作为延迟 0 值。全部探测失败的 IP 不可用；该中位数口径同时用于过滤、排序和扩采触发。
- AC-51：延迟探测默认每 IP 5 次、每次最多等待 1000 毫秒，两项可按任务修改；单次超时作为失败参与失败比例，不自动切换测试方式，也不触发整项任务的自动超时终止。
- AC-52：新任务默认开启延迟→丢包率→下载速度；以中位延迟≤200ms、失败比例≤20%、速度≥5MB/s 判定，阈值边界包含相等值。速度按 1MB＝1000000 字节计算，各项开关及阈值可按任务修改。
- AC-53：新建任务默认选择 ICMP Ping，可以保存为 TCPING；默认 ICMP 不可用时应明确报告并等待使用者手动修改，不静默改用另一种测量方式。
- AC-54：一次运行默认每个已启用地址族最多选择 20 个候选做下载测速，数量可按任务修改，初采和扩采共享该地址族的本次额度；未测速度须标记未测试，不作为 0 速度或已通过下载过滤。
- AC-55：启用下载时，必须先合并初采和扩采中通过已启用延迟／丢包过滤的候选，再统一挑选下载集合；下载步骤不能前移，也不能因初采提前消耗配额而排除尚未完成的扩采结果。
- AC-56：下载候选逐个测试，默认每 IP 最多 10 秒有效下载测量窗口且可按任务修改；速度取实际读取字节数／有效下载时间的平均值，不取峰值。下载失败与未测试分开标记，不能用 0 伪装有效结果。

- AC-59：延迟和丢包过滤关闭时仍执行基础探测；下载关闭时不执行下载测量，速度显示未测而非 0，不能保存速度优先排序，延迟相同按 IP 数值决定。全部基础探测失败的 IP 始终不可用。
- AC-60：主结果可查看全部合格 IP；运行详情可查看所有已纳入预算候选的汇总指标、来源、通过或淘汰／未测／失败状态及原因，不只保留前 10 名，也不为数据保留新增测速。

- AC-67：环境变量密码存在时优先使用并在重启后生效；否则每次启动生成新的随机密码，重启使旧密码失效，不从数据卷恢复旧随机密码。部署者可受保护地获取密码并通过环境变量重置，不提供账号找回。
- AC-68：登录有效期最长 7 天，退出结束当前会话，密码变化使全部旧会话失效；同来源 15 分钟内累计 5 次失败冷却 15 分钟，不锁全站，不记录输入密码。
- AC-69：DNS 和通知服务连接全局维护、任务引用；秘密值只能替换不可明文回读，不进入普通日志或历史快照，所有已认证使用者按共享数据规则使用配置。
- AC-70：DNS 推送只替换明确选中的 A／AAAA 记录 IP；原 TTL、解析线路和其他属性保持不变，任务不能覆盖这些属性，其他记录不受影响。
- AC-71：每任务可同时选择 Telegram 和企业微信，每种关联一个全局连接；新建默认均关闭，配置时不自动发测试消息，消息开关不影响 DNS 推送，每渠道发送状态独立。
- AC-72：启用的渠道仅在执行结束时发一次摘要，覆盖成功、无结果、失败、取消和中断，不通知排队／开始／重复跳过，不重复补发旧结束事件；用户可手动发送记录摘要，消息不包含密钥或伪造指标。
- AC-73：通知失败不自动重试，各渠道留存脱敏原因，可手动单独重发而不重跑测速或 DNS；网络超时结果标记未确认，不能声称未送达，手动重发前提示可能重复。
- AC-74：使用同一数据卷重建或正常升级容器后，任务、服务连接及其受保护凭据、历史和回收站保持；备份恢复不重跑旧执行或重发旧推送，也不恢复旧随机密码，未设置环境变量则启动生成新密码。
- AC-75：探测次数 1～100、单次等待 100～10000ms、下载窗口 1～60 秒；下载开启时数量不得超过该族累计预算；TCPING 默认 443，端口仅接受 1～65535。门槛校验按第 3.7 节执行，无效组合拒绝保存且不静默修正。
- AC-76：连接被任务引用时须解绑才能删除；有排队或运行实例引用时不能变更执行凭据或目标。空闲时可替换凭据，目标身份变化须新建连接重新绑定，不能隐式改变已确认的 DNS 或通知目标。
- AC-77：不同任务可更新同一 DNS 记录，但同目标写入串行、按实际推送顺序生效；可查看最近写入来源和时间，从旧记录人工推送前明确提示可能覆盖较新结果。
- AC-78：DNS 请求超时或连接断开时标记结果未确认，并尝试读取核对明确目标记录；核对成功则记录实际状态，无法核实时不自动重写、回滚或改选目标，人工重试前提示可能重复写入。
- AC-79：单次运行使用排队中、运行中、已完成、无合格结果、失败、已取消、已中断七种主状态，阶段结果另行保存；优选成功后推送失败不覆盖主结果，正常无合格 IP 与执行故障明确区分。
- AC-80：确认排队取消或运行停止后，每个已启用通知渠道最多发送一次“已取消”结束摘要，未启用渠道不发送；该例外不恢复测速或 DNS，也不因取消摘要失败自动重试或撤销已成功的外部操作。
- AC-81：前一执行已保存优选结果，但 DNS、既定结果核对或通知仍在自动处理中时，下一执行不得取得运行席位，同任务重复触发仍按忙碌规则处理；全部自动收尾结束后才按 FIFO 启动下一执行，推送失败或未确认不覆盖已成功的优选主结果。
- AC-82：各目标／渠道的成功、明确失败、结果未确认或跳过均可结束其本轮处理，不等待人工重试或自动重发才释放席位；已取得席位的执行取消时，须确认真正停止并结束允许的取消摘要处理后释放，排队取消不占用或抢占其他执行的席位。
- AC-83：配置最大测量窗口为 10 秒，文件正常完整下载且实际有效测量时长为 3 秒、实际读取 30 MB 时，平均速度为 10 MB/s，而非按配置窗口算为 3 MB/s；该样本可参与原速度门槛筛选，保留实际字节数、实际时长及提前完成标记，不重复下载凑时间。网络错误或异常断流仍按失败处理，不能用部分下载数据套用本规则。
- AC-84：建连、TLS 握手及等待响应头共耗时 1 秒，正文阶段实际经过 3 秒并正常完整读取 30 MB 时，下载平均速度为 10 MB/s，而非把前置等待计入得到 7.5 MB/s；配置窗口从开始读取正文时计时。正文阶段的等待或停滞不得从这 3 秒中扣除，窗口到期主动停止采样与异常连接、读取失败须明确区分。
- AC-85：正文前建连、TLS 握手及等待响应头合计默认最多等待 10 秒，不按阶段分别重置预算；任务仅可保存 1～60 整数秒。前置等待超时只使该 IP 下载失败并记录原因，其他候选继续，不将整项任务标为超时终止；未超时并进入正文时，正文仍拥有其独立配置的测量窗口。
- AC-86：正文测量窗口为 10 秒，前 2 秒读取 30 MB、随后无新增数据且未发生真实读取错误时，不因停滞满 3 秒提前判失败；窗口到期按全部 10 秒计算平均速度为 3 MB/s，并按原门槛筛选，不按前 2 秒算为 15 MB/s，不标记为文件完整下载。
- AC-87：正文全程零字节、无法形成有效正时长或发生真实连接／读取错误时，下载失败并记录原因，不能伪造为 0 速度或用异常前已读取的部分数据充当有效样本；该 IP 失败不停止其他候选，仍区分未测试、下载失败及有效样本未达门槛。
- AC-88：在指定任务内按入队时间范围、主状态及手动／定时来源筛选时，仅返回同时符合已设置条件的该任务记录；未实际开始就取消的记录仍以入队时间命中，不因缺少开始时间被漏掉，也不混入其他任务的记录。
- AC-89：一条主状态已完成的执行，只要任一 DNS 目标失败，就可匹配“已完成＋DNS 失败”；其他目标成功不抹掉该匹配。若另加“通知结果未确认”，须至少有一个通知渠道未确认才返回；DNS 与通知条件独立匹配后同时满足，不把投递异常改写成优选失败。
- AC-90：运行记录列表展示记录 ID、触发方式、入队／实际开始／自动收尾结束时间及执行耗时、主状态、当前阶段和席位忙碌标记；耗时包含自动收尾，收尾尚未结束时不能因已有优选结果而显示席位空闲。未产生或无法确认的时间与指标如实标记，不用 0 或伪造时刻补齐。
- AC-91：列表按各地址族展示合格数量及最终排序第一名的合格 IP，区分未启用、未产生和无合格结果；DNS 多目标混合成功、失败或未确认时，摘要保留异常，Telegram 与企业微信独立显示结果，不能以一个成功覆盖其他目标或渠道的失败。
- AC-92：候选详情按本次配置快照逐步骤对照顺序、启停、阈值、实际汇总指标、判定及原因；修改任务当前规则后，历史阈值及判定不变，停用步骤不得显示为已通过。
- AC-93：因前序淘汰而未执行后续步骤，或未入选下载配额而未测速度时，详情明确说明原因，不用 0 或虚构指标代替，不伪造速度门槛失败；仅最终合格 IP 显示本次该地址族按既定排序所得名次，未合格候选不伪造该名次。
- AC-94：等待队列及运行进度自动更新，下一位执行显示为等待队列第 1 位；排队显示实际等待时长，取得席位后显示当前阶段及包含收尾的运行已用时。各地址族按阶段显示已处理／本阶段已知总量及单位，失败或跳过与合格数量分别呈现，不把已处理误当全部合格。
- AC-95：候选总量尚未确定或扩采仍可能新增候选时，不把累计上限、下载配额或预计值显示为实际总量；显示已知处理量、待确定说明及阶段变化，不提供总体百分比或预计剩余时间，不以 0 或固定百分比伪造进度。
- AC-96：DNS 按目标、通知按渠道更新进展并保留各自实际结果；候选全部测量结束但 DNS／通知仍在自动收尾时，进度继续显示当前阶段及席位忙碌，直到既定收尾结束，不因测量数量已完成而提前启动下一执行。
- AC-97：优选已保存最终结果、DNS／通知仍正常收尾时，主状态仍为运行中且当前阶段可见，已有结果可查；正常收尾有结论后按优选结果定稿，DNS 或通知失败、未确认不将已有合格结果改成优选失败。
- AC-98：正常收尾期间用户停止并确认停止时主状态为已取消，期间重启导致执行中断时为已中断；已有结果及成功外部操作保留，未确认事实不伪造，不重跑或重发，取消摘要和释放席位仍遵守既定规则。
- AC-99：符合条件的自动 DNS 依据已确定的优选阶段结果启动，不以主状态必须先为已完成作前置；结束摘要使用已知优选结论，正常主状态待摘要等收尾处理结束再定稿，不出现双方互相等待或提前释放席位。
- AC-100：系统内关键配置变更、触发／停止、DNS／通知推送或重试及记录删除／恢复／清理产生轻量操作日志，包含事件时间、共享管理身份／系统、动作、非敏感对象、动作结果和脱敏原因；普通列表或详情浏览不产生该类日志，不伪造真实个人身份。
- AC-101：未认证不能查看操作日志；认证使用者共享只读可查范围，按事件时间、动作、对象和结果筛选时同时满足已设条件，不提供逐条修改或删除操作／简要删除日志的能力，不增加独立日志权限角色。
- AC-102：操作／简要删除日志从事件发生起固定保留 30 天，过期自动清理且不进入运行记录回收站；其清理不改变任务、运行历史、DNS 或消息。运行事件及历史继续按原可配置保留期和 7 天回收站处理，不被操作日志规则替代。
- AC-103：替换凭据及外部失败时，仅记录动作、非敏感对象及脱敏结果，不保存旧新秘密、带密钥地址或完整认证原文；触发受理不记为优选成功，外部结果未确认不伪造为成功、失败或未写入。
- AC-104：同数据卷重建或升级后操作日志保持；备份恢复保留原事件时间，不重新起算 30 天，不重放日志所指操作或补发 DNS／消息；超过保留期的日志仍按原时间清理，不因恢复而延长存续。
