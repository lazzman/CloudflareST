## 3. 未关闭问题

### POST-RC-01 · P2：过时通知重试资格缺少服务端校验

**依据**：UX R3 §4.4 明确“已成功渠道不随重发失败项再次发送”（`docs/ip-optimization-ux-ui-v0.1-review.md:168`）。AC-73 是关联规则，不将“仅允许重试最新尝试”伪称为 AC-73 的原文。

**实现差异**：`internal/management/connections.go:403` 的重试分支只判断被引用的旧尝试是 `failed`／`unconfirmed` 及风险确认，未核对同渠道是否已有后续成功或在途尝试。首次发送分支才检查当前渠道状态。前端 `internal/management/web/src/lib/notifications.ts:12` 已限制过时尝试，但旧页面或另一客户端可绕过前端限制。

**已执行的反例**：

1. 同一运行、同一 Telegram 连接：首次尝试 A 失败，重试 B 成功。
2. 经认证的本地 HTTP 请求使用新操作号，再次引用 A 并确认重试风险。
3. 实际返回 HTTP 202，并产生第三次模拟 `Notify` 调用；预期应拒绝过时重试而不新建投递。模拟调用累计 3 次，其中首次失败、后两次成功；DNS 调用为 0。
4. B 为 `pending`／`dispatching`／`running` 时，再引用 A 也均受理。三个子场景只执行事务内受理检查并回滚，没有实际发送，不能表述为已动态证明并发重复送达。

**影响与边界**：旧页面操作可导致成功渠道再次发送，或为同渠道在途重试叠加新投递。这是服务端业务重试资格缺口，不是同号幂等失效、越权漏洞或远端“恰好一次”保证失败；本轮没有真实消息发送。风险确认不能替代当前重试资格检查。

**建议修复，尚未实施**：在创建投递的同一事务中，核对该运行、该渠道的最新尝试；只有最新尝试失败／未确认且原连接及风险条件有效时才可重试。同渠道已有后续成功或在途尝试时返回冲突且不新建投递。保留原失败事实、取消摘要限制及同号幂等。新增成功后旧引用、三种在途状态、最新合法重试及并发提交回归。

**证据**：[反例代码](post-rc-audit-2026-11-15/management_audit_test.go.txt)、[执行输出](post-rc-audit-2026-11-15/new-counterexamples.txt)。两个相关顶层用例失败，其中第二个包含三个在途子场景。

### POST-RC-02 · P3：前端增加 PRD 未定义的延迟阈值上限

**依据**：PRD §3.7（`docs/ip-optimization-prd-v1.0.md:205`）要求延迟上限为大于 0 的有限数，AC-75 引用该门槛规则；未规定 60000ms 上限。

**实现差异**：后端 `internal/optimizer/config.go:45` 按有限正数校验；前端 `internal/management/web/src/lib/domain.ts:153` 和 `internal/management/web/src/pages/TaskEditorPage.vue:66` 额外设置 60000 上限。

**已执行的反例**：其他配置合法时，输入延迟阈值 60001ms。后端临时数据库保存成功，未启动测速；实际 Vue 表单阻止保存，显示“请输入大于 0 且不大于 60000 的数值”，业务写请求为 0。浏览器采用隔离环境，无外部请求和页面脚本错误。

**影响与边界**：页面无法保存契约允许的配置，属于低风险前后端一致性问题；不是后端保存失败、测速算法错误或测量结果错误。单次探测等待另有最大 10000ms 约束，不能将本项夸大为常规测速不可用。

**建议修复，尚未实施**：移除表单与 `validateTask` 的额外上限，统一为有限且大于 0；保留 0、负数、无穷大和非数字拒绝。增加 60001 可保存及非法值拒绝的前端／后端契约回归。如确需新上限，应走需求变更，不能用当前实现倒改 PRD。

**证据**：[后端保存输出](post-rc-audit-2026-11-15/new-counterexamples.txt)、[页面观测](post-rc-audit-2026-11-15/ui-observations.jsonl)、[页面复现脚本](post-rc-audit-2026-11-15/check-ui.mjs)。页面脚本正常退出只表示完成观测，不表示该功能通过。
